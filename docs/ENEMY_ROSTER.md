# Enemy Roster — subclass audit

All 45 combat enemies extend `EnemyBase` (`scripts/enemies/enemy_base.gd`), a CharacterBody3D
state machine (IDLE/PATROL/ALERT/CHASE/ATTACK/STAGGER/DEAD) with a `Damageable` child (`hp`).
(`enemy_bomb.gd` is excluded: it is a lobbed bomb projectile extending `Node3D`, not an enemy.)

Two base-class conventions make the flags in this table matter:

1. **Stats are hardcoded in `_ready`.** Every subclass writes its real `max_health` /
   `move_speed` / `attack_cooldown` in its own `_ready` (by convention after
   `super._ready()`). Elite affixes and campaign difficulty therefore must never write
   stats directly — they stack `_health_mult` / `_speed_mult` / `_cooldown_mult`, which
   `_sync_stats` re-applies **deferred** so it lands after the subclass body has run.
   Writing stats pre-`add_child` gets clobbered; `Elite.apply` / `apply_nemesis` must run
   before `add_child`.
2. **Overriding `_on_died` / `_state_attack` without `super` silently drops base logic.**
   This is the repo's most recurring bug class (barks, bounty payoff, loot, kill credit,
   codex discovery have all been bitten by it). 7 subclasses override `_on_died` and 11
   override `_state_attack` without calling super — so any **new** base-class death or
   attack feature must hook the `hp.died` / `hp.damaged` signals instead of extending
   those methods (see the `mark_bounty` / `_on_died_voice` pattern in `enemy_base.gd`).
   The one deliberate exception is the weapon kill style (`KillFx`): it lives in the base
   `_on_died` because it *replaces* the base death visuals. Of the 7 overrides, DRONE (and
   its children), RAPTOR, MENDER and SKITTER read it themselves through
   `_kill_style()` / `_prep_kill_fx()`; SEEKER keeps its shot-down blast (that blast is a
   mechanic) and the bosses ARCHON and OVERSEER keep their deaths.

**Armour class.** Every enemy type here also has an armour class (CHASSIS, HEAVY PLATE,
LIGHTWEIGHT, NETWORKED) that scales player weapon hits by the gun's damage class. The
source of truth is `DamageMatrix.ARMOUR` in `scripts/weapons/damage_matrix.gd`, keyed by
`codex_key()`; a new enemy needs a row there or `tests/weapon_matchup_probe` fails.

Salvage drops: the GUNNER drops its SIEGE Chaingun and the MECH its PALM Cannon when it
dies (`Salvage.TABLE` in `scripts/weapons/salvage.gd`, keyed by `codex_key()`), one magazine
for the player to pick up. The drop hangs off `hp.died` in `EnemyBase._ready`, so an
override of `_on_died` cannot lose it. A new heavy with a gun worth taking: add a row there.

Column notes: "Overrides w/o super" lists only overrides that do **not** call
`super._on_died(...)` / `super._state_attack(...)` / `super(...)` — an override that calls
super is safe and not listed. A `†` on the script means its `_ready` sets stats **before**
calling `super._ready()` (deviates from the documented order; functionally harmless today,
because base `_ready` reads the already-set vars and `_sync_stats` is deferred past the whole
`_ready` chain either way — but keep new base `_ready` logic order-insensitive). Scripts that
extend an intermediate class (`EnemyDrone`, `EnemyAndroid`, `EnemyDog`, `EnemyColossus`)
inherit that parent's overrides too.

via `GameState.announce_boss`.

**Boss presence:** every boss has a `boss_name` and a `boss_epithet` (translated; the
strings check fails on an epithet without a row). On `announce_boss` the HUD's
`BossPresence` (`scripts/ui/boss_presence.gd`) plays an intro card: letterbox, warning
header, name, epithet. A phased boss lists the HP fractions where its fight escalates in
`boss_phase_marks()` (66 % and 33 %; ARCHON 67 % and 34 %; TERMINATOR one, 50 %, its OVERCLOCK) and its
`_phase()` returns `boss_phase()`, so the boss bar's notches sit exactly where it really
escalates. Crossing a mark fires `EnemyBase._boss_phase_beat` off `hp.health_changed`
(override-proof): a roar ring that leaves cover standing, the alarm, a quake, a beat of
hit-stop, and `GameState.boss_phase_changed`, which the HUD banners ("PHASE II",
"FINAL PHASE"). A new boss needs an epithet, a strings row and, if it escalates, marks
(`tests/boss_presence_probe`).

**Moving parts on static models:** a GLB without a rig can still move a part if it is its own mesh. `PartRig` (`scripts/enemies/part_rig.gd`) poses a part by a transform built in the robot's body frame (conjugated into the part's parent frame, so the fit, RobotModel's lean and import scale carry through), and `PartRig.split_x` cuts a mesh that holds a left and a right copy into two (`split_groups` into any number in one pass, always from the original mesh: splitting a split copy again gave garbage triangles). Used by the HOWITZER's barrel (its own conjugation) and legs, the RONIN's revolvers and katana, the DOG's legs, the ENFORCER's rifle, the GUNSLINGER's gun-arm and the BREAKER's hammer (already its own mesh: `PartRig.entry` + `pose`, no cut). A big mesh is cut offline instead (`tools/blender/split_regions.py`; `split_groups` took about 1.3 s on BEHEMOTH-X's 337k triangles): BEHEMOTH-X's arms and legs, APEX ENDOFRAME's gun arms, barrel clusters, thighs and shins, and the ROLLER's wheel and arms: not for size, but because reading `wheeled_robot.glb`'s vertices back from the renderer in a windowed run returns hundreds of garbage positions (headless it is clean; the HOWITZER's and DOG's meshes read clean in both), so a runtime split covered the screen in spikes. A new part rig on an untested GLB should check a windowed shot of the split before trusting `split_groups`; `split_regions.py` regions can be narrowed to a cylinder (the wheel) as well as a box. `AimedPart` (`scripts/enemies/aimed_part.gd`) swings a part about a pivot onto a target and back (ENFORCER, GUNSLINGER). Measure parts only after RobotModel's deferred fit has landed.

**Muzzles on the gun:** an enemy fires from its `muzzle` node, and a fixed `Muzzle` in the
scene drifts off the model's gun as it animates (or never was on it). Two ways to pin it to
the model: `muzzle_on_bone(bone, offset)` in code (MECH palm, SENTINEL and BOWLER throwing fists, ANDROID face lens,
SNIPER's two barrels, WARMECH's two shoulder cannons), or the scene exports `muzzle_bone` +
`muzzle_bone_offset` on any `EnemyBase` (HUNTER, DIFFUSION, OVERFITTER, DEEPFAKE, HIVE and the
QUANTIZER flyer fire from their Quaternius `Gun` bone this way). Either way the muzzle is placed
from the skeleton's current bone pose (`bone_point`), not the BoneAttachment3D's own transform,
which refreshes a pose late and put a banking flyer's shots up to 1.2 m off its gun. Measure the offset from the model: the vertices
skinned to the bone, front-most along the bone's own +Z (`tests/gun_muzzle_probe.gd`
`_barrel_front`), not by eye. HUNTER's and OVERFITTER's guns have twin barrels: `muzzle_bone_offset_alt` holds the
second, and their fire code calls `next_barrel()` after each round to alternate (it leaves
the live muzzle flash on the barrel it came from).

**Tallies:** 45 subclasses. `_on_died` overridden without super: **7** (ARCHON, DRONE,
MENDER, OVERSEER, RAPTOR, SEEKER, SKITTER — matches the "seven subclasses" comment in
`enemy_base.gd`). `_state_attack` overridden without super: **11** (ALIEN, ANDROID,
COLOSSUS, DRONE, MANUS, MECH, RAPTOR, SEEKER, SHARK, SMASHER, TERMINATOR). Overrides that
correctly call super: `_on_died` — COLOSSUS, MANUS, OPTIC, ORB, SMASHER, TERMINATOR;
`_state_attack` — OPTIC, RIPPER. `†` (stats set before `super._ready()`): 12 scripts.
